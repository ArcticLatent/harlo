# Keep OpenWiki; shrink Harlo’s runtime first

**Decision: retain Harlo’s working OpenWiki integration and fund a bounded 1–2 person-week native-retrieval experiment; do not replace it wholesale with llm-wiki now.** The Node concern is substantial: Harlo’s prepared wiki runtime occupies **210.3 MiB apparent / 256.4 MiB allocated**, transfers as **65.9 MiB gzip**, and its isolated MCP process measured about **292 MiB median RSS**. Those costs justify engineering investment, even though tiny warm searches already take about **4 ms**. llm-wiki genuinely offers a Node-free engine, but neither its complete equivalent deployment footprint nor comparative latency, memory, tokens or answer quality has been demonstrated. Its lack of internal LLM generation is **not** the blocker: Harlo already supplies generation through its selected agent; the expensive compatibility work is preserving evidence, claims, freshness, workspaces, section retrieval and resumable updates. Change the replacement decision only after a compatible implementation proves those invariants and meaningful resource savings; a hard Node-free requirement would justify funding a larger native lifecycle port, with the same parity gates. ([Bundled measurements](file:///tmp/opencode/harlo-wiki-probe-5elgy6h6/results.json), [host-agent workflow](https://github.com/ArcticLatent/harlo/blob/563992a39e12a546d13170faa8d118719becd2ad/crates/harlo-app/src/workspace.rs#L2409-L2463))

Harlo’s architecture today is:

```text
Desktop Rust/QML or iOS Swift UI
  → Harlo project settings, selected agent/model/auth/budget
  → host agent investigates source and writes assigned Markdown

  → persistent bundled Node: openwiki … mcp --host harlo

  → openwiki/*.md + .claims/ + .run.json + manifest/update metadata
  → native Harlo page renderer, citations, graph, progress and phone APIs

Ordinary agent retrieval → same adapter → OpenWiki section search/read
Desktop/phone search → OpenWiki first → native substring fallback on error
```

What ingest does not replace is OpenWiki’s deterministic orchestration: source snapshots, sparse claim reconciliation, durable per-page completion and finalization. Harlo’s real metadata recorded eight pages and a completed `host-agent/harlo` update; replacing a proven workflow therefore requires more than adapting page CRUD. Candidate accounting must include embedded stock schemas, external `libz`, `libgcc_s`, libc/libm and loader, configuration/custom schemas, persistent Tantivy indexes and graph snapshots, and Git for history; source/wiki data and the host agent remain necessary. Stock schemas are embedded, but cache/shared-library costs were not totalled. The binary supports CLI/library/MCP/ACP/search/graph without crate-level feature splits; it supplies **no OpenWiki-compatible evidence lifecycle**. Consequently **23.94 MiB is not the price of equivalent functionality**, and subtracting it from Harlo’s bundle would overstate a verified saving. Main’s lock has 465 package entries including root; Rust removes Node deployment, not dependency maintenance or native build requirements. ([Manifest](https://github.com/geronimo-iia/llm-wiki/blob/f42c5898877e2fefde54e29c4772ec3f4cde0feb/Cargo.toml), [embedded schemas](https://github.com/geronimo-iia/llm-wiki/blob/f42c5898877e2fefde54e29c4772ec3f4cde0feb/src/space_builder.rs#L1-L104), [artifact libraries](file:///tmp/opencode/llm-wiki-research/artifact-inspection.json), [persistent storage](https://github.com/geronimo-iia/llm-wiki/blob/f42c5898877e2fefde54e29c4772ec3f4cde0feb/src/engine.rs#L135-L175))

Harlo already bundles Node rather than requiring system `node`/`npx`. `packaging/openwiki/fetch.sh:23–106` pins/checksums Node, installs locked production dependencies, applies patches and prunes maps/declarations/docs. The upstream unpruned census is therefore **not another available 93 MiB saving**. Local updates ship through Harlo’s versioned bundle; remote deployment in `openwiki.rs:537–585` uploads the entire gzip tree, atomically caches it, and smoke-tests `better-sqlite3`. It currently rejects cross-architecture hosts and retains the 65.9 MiB compressed buffer in Harlo after first packing. Native deployment could simplify this, but needs pinned binaries, library compatibility, atomic update/rollback and architecture coverage; actual AppImage/deb/rpm savings remain unmeasured. ([Packaging](https://github.com/ArcticLatent/harlo/blob/563992a39e12a546d13170faa8d118719becd2ad/packaging/openwiki/fetch.sh#L23-L106), [remote deployment](https://github.com/ArcticLatent/harlo/blob/563992a39e12a546d13170faa8d118719becd2ad/crates/harlo-core/src/openwiki.rs#L537-L585))

Removing wiki Node leaves Qt/QML, Rust SQLite, media/fonts, optional context-mode’s Node, user-configured `npx` MCPs and some language servers. Browser Mermaid/phone JavaScript is separate from Node. A retrieval-only JS facade retains Node; a native reader with the old writer retains its distribution unless writer delivery becomes optional. OpenWiki rebuilds in-memory FTS using **`node:sqlite` on each query**; the bundled `better-sqlite3` serves other dependencies. Candidate persistent indexing offers a plausible optimization but adds invalidation duties. Neither search engine uses embeddings or query-time models. Generation tokens remain host-agent costs: whole-page reads or extra tool turns could outweigh lower backend latency. **No measured token or quality saving exists here.** ([Other Node use](https://github.com/ArcticLatent/harlo/blob/563992a39e12a546d13170faa8d118719becd2ad/crates/harlo-core/src/mcp_catalog.rs#L1-L54), [current retrieval](https://github.com/langchain-ai/openwiki/blob/41c92c4a00d6dadaa3769c6bf93023ed5a618076/src/retrieval/wiki.ts), [candidate retrieval](https://github.com/geronimo-iia/llm-wiki/blob/f42c5898877e2fefde54e29c4772ec3f4cde0feb/src/search.rs#L172-L328))

## Compatibility depends on evidence and sections, not tool renaming

The following source-grounded parity map compares the actual Harlo contract with candidate primitives. “Missing” means absent from the inspected contract, not impossible to implement.

| Capability | Harlo + patched OpenWiki | llm-wiki and required adaptation |
|---|---|---|
| Generation ownership | Harlo-selected agent/model/auth/budget researches and writes. | External-agent model fits; retain Harlo’s authoring workflow. |
| Search granularity | Heading units; source-path priority, term coverage, weighted FTS5; short hits. | Persistent Tantivy page BM25 × status × confidence. Requires heading-level ranking/refs; `include_sections` concerns section-index pages. |
| Precise reads | Requested anchors, ordered complete sections, optional recorded provenance. | Whole-page `wiki_content_read`; no equivalent section argument. Adapter must preserve bounded disclosure. |
| Tool/transport contract | Ten `openwiki_*` tools, structured/text JSON, host-injected root; only two normally exposed. | **25 observed tools**, despite README’s 24; different names/arguments/envelopes. Raw `serve` would fail Harlo’s required-tool handshake. |

| Freshness/invalidation | Source fingerprints, dirty/untracked inputs, ignore rules, evidence preflight, per-page baselines. | Index Git/schema freshness and age/confidence lint; watcher indexes wiki edits, not changed application semantics. |

OpenWiki’s value is concrete: the no-model fixture retained an evidence version after inserting a line above its cited range, but marked the original evidence unresolved after renaming the source file. Its resolver relocates unchanged ranges **within a file**, not across arbitrary renames. “Verified” means evidence/version/durability checks, **not semantic entailment or complete topic coverage**. Candidate age/confidence lint cannot replace this, and indexing imported pages must not mark them newly verified. ([Executed lifecycle](file:///tmp/opencode/openwiki-upstream-assessment/probe-results.json), [evidence resolver](https://github.com/langchain-ai/openwiki/blob/41c92c4a00d6dadaa3769c6bf93023ed5a618076/src/claims/evidence/repository/resolver.ts))

Smooth interaction also requires preserving honest limitations. Harlo polls progress and offers source-driven updates without automatically spending model tokens. Its MCP client ignores unsolicited notifications; timeout is not backend cancellation. OpenWiki supports one active host lifecycle per manager, not proven independent concurrent writers. Linked agent search/read exceeds current desktop cross-wiki page-reader support. An adapter should preserve existing guarantees and test these boundaries, rather than promise capabilities neither baseline establishes. ([Progress/offers](https://github.com/ArcticLatent/harlo/blob/563992a39e12a546d13170faa8d118719becd2ad/crates/harlo-core/src/openwiki.rs#L776-L923), [transport](https://github.com/ArcticLatent/harlo/blob/563992a39e12a546d13170faa8d118719becd2ad/crates/harlo-core/src/openwiki.rs#L254-L393), [session manager](https://github.com/langchain-ai/openwiki/blob/41c92c4a00d6dadaa3769c6bf93023ed5a618076/src/integrations/core/session-manager.ts))

## Buy a bounded experiment before buying a migration

**A small native Harlo layer implementing the existing retrieval contract is the most practical first investment.** Harlo already has Markdown readers, rendering, transport and bundled SQLite; matching FTS5 sections/workspace semantics avoids importing an entire second schema/config/graph system. Borrow llm-wiki’s compact output, schema and index-recovery ideas where useful; adopting its whole engine is not a prerequisite for eliminating Node eventually. ([Existing native dependencies](https://github.com/ArcticLatent/harlo/blob/563992a39e12a546d13170faa8d118719becd2ad/crates/harlo-core/Cargo.toml#L13-L30))

These are **planning estimates**, not verified delivery forecasts: one experienced Harlo/Rust engineer, Linux first, existing UI retained, fixture-based verification and x64/ARM64 packaging for production. Ranges are alternative scopes, not additive commitments; upstream waiting time is excluded.

| Investment | Estimated person-weeks | Benefit and limitation | Confidence |
|---|---:|---|---|
| Keep/prune/lazy-load incumbent | **1–3** | Trace headless imports, validate pruning, consider idle eviction and release retained remote tar bytes. Preserves lifecycle; Node remains. | Medium; savings unknown. |
| Retrieval-only facade, existing writer | **2–4 local; 4–6 production** | JS isolation has measured promise; native implementation can avoid Node for reads. Linked workspaces, invalidation and remote rollout extend scope; writer still needs Node. | Medium to medium-low. |
| Optional llm-wiki backend | **3–6** | Constrained read/content backend for selected projects or new knowledge spaces. Shipping both by default increases footprint. | Medium-low. |
| Native existing OpenWiki contract | **8–14** | Retain generator/data; port deterministic claims, queue, resolver, drift and finalization. Can ultimately remove wiki Node. | Low-medium. |
| Full llm-wiki schema migration with parity | **10–18** | Adds schema/identity migration and compatibility lifecycle to candidate integration, plus rollback. Highest ownership risk. | Low. |

Authorize **one 1–2 person-week proof of concept**, preserving the working default. Freeze the exact patched bundle and create isolated 2/50/500/2,000-page fixtures, including headings, source links, ignored/stale claims, deleted/renamed pages and ambiguous linked workspaces. Compare current MCP with one native section-search/read adapter; use the existing JS facade as an import-cost control and the pinned candidate only where it fits that adapter. A scripted, model-free host should capture begin/plan/submit/finish and interruption behavior; it should not attempt to implement the full lifecycle in this budget. Existing Harlo fixtures at `crates/harlo-core/src/openwiki.rs:1251–1581` and UI scenarios provide the initial contract. At the deadline, **abandon candidate-based replacement if preserving evidence and section/workspace behavior requires a broad schema rewrite, if correctness gates fail, or if measured benefits are too small to justify maintaining another backend**. Keep useful benchmark fixtures and pursue the cheapest passing packaging/read-path improvement. Full migration requires a later matched model/task evaluation, counting generation amortization, maintenance, cached tokens, answer success and extra source reads; no paid calls are needed for this first decision gate. Opportunity cost matters: a 10–18 person-week compatibility project displaces Harlo product work for an unproven improvement over already-fast warm retrieval.

## Conclusion

The useful architectural boundary is **Harlo’s evidence contract**, not the language of the executable behind it. Treat Node removal as a measurable distribution and residency objective: native retrieval can earn its place independently, while a future native writer must earn ownership of durable evidence. llm-wiki is a source of useful components and an optional backend candidate; today it is not the lowest-cost route to an equivalent, reliable Harlo wiki.
